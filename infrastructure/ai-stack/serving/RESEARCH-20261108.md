# SGLang serving profile research: Qwen3.8-27B Quark MXFP4 + DFlash2 on 2x Radeon AI PRO R9700

> **Addendum, 9 November 2026.** The body below is unchanged research. Where it differs from [`qwen3.8-27b-mxfp4-tp2.json`](qwen3.8-27b-mxfp4-tp2.json), the profile is authoritative. On 2026-11-09 the owner made arm A (here "Profile A": `no_buffer` + `--disable-overlap-schedule`) the bring-up baseline; arm B ("Profile B", `extra_buffer_lazy` with overlap on) is the first experiment after it, not the bring-up target. The served name is `Qwen3.8-27B-MXFP4`; Appendix A's `--served-model-name qwen3.8-27b` would fail `qualify.py`'s served-name check.

Research date: 2026-11-08. Research only; no repository files, services, GPUs or Kubernetes objects were touched.
Upstream source was read at the pinned commit `fcb3274646e43c16d70fd83806ebb3a5134d5e81` (read-only `git archive`/`git show` over SSH, extracted to the session scratchpad). Local evidence: the op234 selection record, its launch adapter, the serving-repo docs on `origin/main`, the workstation docs and manifests.

Evidence classes used throughout:

- **V** verified in the pinned upstream source or a primary document (model card, config.json, AMD docs).
- **M** measured earlier on this hardware (op149-op234 evidence in the serving repo). Those runs used an older stack; they are guidelines, not results for the new stack.
- **W** web/community report; treated as a lead, not as truth.
- **I** inference from V/M/W; stated as such.

## 0. Executive summary

1. **One op234 flag is now a startup error.** `--enable-linear-replayssm-spec` with `--speculative-algorithm DFLASH` is rejected at this pin for non-KDA models: `KVCacheConfigurator._validate_replay_spec_algorithm` raises `"--enable-linear-replayssm-spec with DSPARK/DFLASH requires a KDA model"` and is called from `_build_hybrid_req_pool` (the path Qwen3_5 takes). The upstream PRs that would wire GDN+DFLASH through the ReplaySSM fold (#36683, #35725) are not merged. Drop the flag. Consequence: the DFLASH verify now needs the per-draft intermediate SSM buffer again, roughly 1.7 GiB per card at fp32 for 2 running requests, which op234 did not pay. (V)
2. **`extra_buffer` is now supported on HIP** (`_platform_supports_mamba_cache_extra_buffer` includes `platform.is_hip`, from PR #30359 merged 2026-07-15, CI-tested on MI300/MI350 only). With the default `auto` strategy and the overlap scheduler left on, the new stack resolves to `extra_buffer` by itself; `extra_buffer_lazy` (one fewer slot per request) is also admitted with DFLASH ("dflash gained the hook in DFlashVerifyInput.prepare_for_verify"). op234's `no_buffer` + `--disable-overlap-schedule` was a compatibility requirement of the old image, not a tuning result. This is the main candidate for a measured change; it is untested on gfx1201. (V, W)
3. **Default attention on HIP is still `aiter`**, which is not installed and is AMD's documented failure case on Radeon. `--attention-backend triton` remains mandatory. `SGLANG_USE_AITER` now defaults to `false`; `SGLANG_USE_AITER_MHA`/`_MOE` no longer exist. (V)
4. **Custom all-reduce must stay disabled.** The HIP dispatcher falls back from the missing AITER kernel to SGLang's own HIP custom all-reduce, which assumes IPC/P2P and has no RDNA4 release/acquire fix (vLLM needed one for correctness over non-coherent PCIe). Without dma-buf P2P on gfx12 the safe path is RCCL. (V, W)
5. **Memory is tighter than op234.** Per card at `--mem-fraction-static 0.92` the previous profile used 28.82 of 31.47 GB; adding the ~1.7 GiB intermediate buffer overshoots. Levers, in order of least quality risk: `--speculative-draft-kv-cache-dtype fp8_e4m3` (-1.25 GiB), lower `--max-total-tokens`, `--mamba-ssm-dtype bfloat16` (-1.6 GiB, accuracy-gated). The first GPU start decides. (I from V+M)
6. Everything else in op234 is still justified on the new stack with small changes: add the two parsers and a server-side default `reasoning_effort=low`, keep `chunked-prefill 2048`, bf16 KV, fp32 LM head, decode graphs for bs 1-2 only, prefill graphs disabled (the HIP default), RCCL on `lo`, offline HF.

## 4. Differences from op234 and why

1. **Remove `--enable-linear-replayssm-spec`** (startup error for DFLASH on GDN at this pin). Budget the intermediate SSM buffer it used to skip.
2. **Mamba radix strategy becomes a measured choice**: Profile B `extra_buffer_lazy` + overlap scheduler (now supported on HIP, the stack's own `auto` result) versus Profile A `no_buffer` + `--disable-overlap-schedule` (op234's forced compatibility setting).
3. **Add the parsers and the server-side default template kwargs** (`qwen3`, `qwen3_coder`, `enable_thinking=true`, `reasoning_effort=low`); op234's CLI served a benchmark harness that parsed itself.
4. **Drop dead environment**: `SGLANG_USE_AITER_MHA/MOE` (gone), `SGLANG_DISABLE_DRAFT_EXTEND_CUDA_GRAPH` (no effect on DFLASH v2), `ROCBLAS_USE_HIPBLASLT=-1` (undocumented; auto is equivalent).
5. **Add observability defaults** for production (`--enable-cache-report`, `--decode-log-interval 40`).
6. **Memory levers are new**: `--speculative-draft-kv-cache-dtype fp8_e4m3`, `--mamba-ssm-dtype bfloat16`, `SGLANG_OPT_MAMBA_SKIP_DECODE_LOCK`, and NFS prefetch/overlap loading; none are in the baseline until measured.
7. Everything numerically load-bearing in op234 (Triton attention, bf16 KV, fp32 head, 2048 chunks, 128K/262144 pools, 19 slots, cap3, bs 1-2 decode graphs, RCCL) is retained with a new justification.

## 5. Per-card memory worksheet (estimates; the first GPU start settles them)

Per card, TP=2. GDN slot = 48 layers x 24 heads x 128 x 128 x 4 B + conv state ~= 77 MB (cookbook: 153.9 MB at TP1). Target KV = 16 layers x 2 heads x 256 x 2 x 2 B = 32 KiB/token. Draft KV = 5 layers x 4 heads x 128 x 2 x 2 B = 10 KiB/token.

| Component | op234 (measured/derived) | New profile, Profile B, fp32 state | Lever |
| --- | --- | --- | --- |
| Weights + fixed runtime (target MXFP4, vision, lm_head, embeddings, draft bf16, graphs) | ~16.9 GB (28.82 - pools) | ~16.9 GB | `--language-only` (-0.8) |
| Target KV, 262144 tokens | 8.0 GiB | 8.0 GiB | `--max-total-tokens` 229376 (-1.3 with draft) / 204800 (-2.3) |
| Draft KV, 262144 tokens | 2.5 GiB | 2.5 GiB | fp8 draft KV (-1.25) |
| GDN slots (19+1) | 1.43 GiB | 1.43 GiB | bf16 state (-0.7); fewer slots |
| DFLASH intermediate SSM states: `(min(2, 19//S)+1) x 8` slot-equivalents | 0 (ReplaySSM) | ~1.72 GiB | bf16 state (-0.86) |
| Total vs static budget 0.92 x 31.47 = 28.95 GB | 28.82 | ~30.5 -> **~1.6 GB short** | apply levers in the order: fp8 draft KV, then max-total-tokens, then bf16 state |

Reading the formula at the pin (`kv_cache_configurator.py:3440-3470`): with an explicit `--max-mamba-cache-size`, the intermediate reserve is `stage_per_req x (capped_reqs + 1) x D`, where `capped_reqs = min(max_running_requests, K // S)`. With K=19 and 2 running requests it is 3 x 8 = 24 slot-equivalents regardless of S. Decision rule: if the start log reports `max_total_num_tokens < 262144`, apply the levers in the order above and re-read the log; stop at the first configuration that reaches 262144 with at least 1 GiB of free device memory after warmup.

Host memory: 19.8 GB target + ~3.2 GB draft pass through page cache (dropped after load), plus two ranks' RSS. Prefetch keeps the single-shard target file in page cache once instead of letting both ranks fault it from NFS concurrently; the pod memory limit (38 GiB in the dual-GPU profile) must cover the transient.

## 6. Prioritised GPU measurement plan

Common rules: one variable per A/B; same request set; both arms from a fresh start; record `amd-smi` power cap (235 W as before), junction temperature, VRAM drift; capture the resolved server args and the startup log lines for attention backend, mamba strategy, `max_total_num_tokens`, `max_mamba_cache_size`, `intermediate_ssm_state_cache size`, graph capture time, RCCL transport (`NCCL_DEBUG=INFO` once). Guard against the known bimodal-clock state on R9700 (ROCm issue #6347: ~21% decode-rate split fixed at process start): measure a 1K-token greedy decode rate right after readiness and discard/restart a start that lands in the slow band before comparing arms.

## 7. Open risks and unknowns

1. **`extra_buffer*` on gfx1201 is unvalidated.** Upstream CI covered MI300/MI350. The Triton FLA prefill writes state checkpoints; a wave32 miscompile would show as wrong cached-prefix answers, which the repeat/branch equality test is designed to catch.
2. **Triton 3.9 on gfx12.** Triton 3.6 had an AMD pipeliner use-after-free that hung FLA/GDN kernels at `num_stages >= 2` on gfx1201 (SageAttention #365; field reports). The new stack pins a later ROCm/triton; op234 ran GDN prefill on its own newer Triton. Treat a hang at first prefill as this class and A/B `TRITON_DISABLE_AUTOTUNING=1` before anything else.
3. **RCCL on gfx12 PCIe.** The LL deadlock (rocm-systems #5480) has partial fixes merged in June 2026; the blanket "force Simple" PR (#2187) was still open in the mirror on 2026-08-20. Fallback is `NCCL_PROTO=Simple`.
4. **Memory shortfall without ReplaySSM** (§5); the exact weight footprint on the new stack is unknown until the first start.
5. **hipBLASLt on gfx1201**: ROCm 10.0 listed training faults (workaround `TORCH_BLAS_PREFER_HIPBLASLT=0`), resolved in 10.1.0; the nightly should include it. Keep the A/B in reserve.
6. **Bimodal decode speed per process start** on R9700 (ROCm issue #6347, open as of 2026-10-20). Benchmark noise and user-visible; the plan screens for it.
7. **DFlash at very long context**: a community v0.5.22 report saw DFlash drafts collapse near 256K while a DSpark draft held. Our own 120K decode at ~107 tok/s on op167-174 contradicts a collapse at 128K; verify at 120K on the new stack.
8. **`reasoning_effort` plumbing**: `--default-chat-template-kwargs` merge and `request.reasoning_effort` fill are verified; the final kwarg name the template receives should be confirmed by rendering one prompt (the template reads `reasoning_effort`).
9. **Exa agent discrepancy**: an Exa multi-step sweep reported several features as unmerged (HIP extra_buffer, compact extend attention, DFLASH block verification). The pinned source contains them; the source was treated as authoritative and the sweep's negative statuses discarded.
10. **Transformers version in the new stack** was not captured in `stack.lock`; the checkpoint's `chat_template.jinja` and `tokenizer_config.chat_template` are equivalent, so either loader path yields the same prompt. The AMD 7.2.1 Radeon note about transformers 5.1.0 failures concerned Janus Pro, not this path.
11. Not verified here: that `SpeculativeAlgorithm.DFLASH.supports_mixed_chunk()` is true (the validation hook will say so at startup), and the exact effect of `--startup-weight-load-mode overlap` on NFS.
